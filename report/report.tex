\section{Phase 2 : Mutex Synchronization}

\subsection{Program Description}
Phase 2 improved our program from Phase 1 by including mutex locks to protect shared data. Each bank account now has mutex locks which a thread must aquire before modifying the account balance. After aquiring the lock and making their changes to the account, the lock is released. This prevents race conditions and ensures only one thread at a time can change and account.

\section{Phase 3: Deadlock Creation}

\subsection{Program Description}
Phase 3 demonstrates how a deadlock occurs when multiple threads attempt to lock shared resources. In this program a thread needed to lock the source and destination, but got stuck when it only had one lock and another thread had the other. Both threads were stuck waiting on each other's lock causing a deadlock.

\subsection{Reflection Questions}

\textbf{Q3.1 Coffman Conditions}

\textbf{Answer:}
Deadlock occurs when all four Coffman conditions are met:

\textbf{1.Mutual Exclusion}
Each bank account is protected by a mutex lock. This prevents mutlitple threads from changing a same account simultaneously.
\begin{lstlisting}[language=C]
pthread_mutex_lock(&accounts[from_id].lock);
\end{lstlisting}

\textbf{2.Hold and Wait}
A thread would lock one account and then will try to lock another while still having the first lock.
\begin{lstlisting}[language=C]
pthread_mutex_lock(&accounts[from_id].lock);
pthread_mutex_lock(&accounts[to_id].lock);
\end{lstlisting}

\textbf{3.No Preemption}
If a thread aquires a lock then it cannot be taken away unless it releases it.
\begin{lstlisting}[language=C]
pthread_mutex_unlock(&accounts[from_id}.lock);
\end{lstlisting}

\textbf{4.Circular Wait}
This is when two threads wait on each other in a circular chain. It prevents either thread from continuing.
\begin{itemize}
\item Thread 1 holds Account 0 and waits for Account 1
\item Thread 2 holds Account 1 and waits for Account 0
\end{itemize}

\subsection{Reflection Questions}

\textbf{Q4.1 Breaking Circular Wait}

\textbf{Answer:}
Lock ordering prevents deadlock by making all threads acquire the locks in order. In our program, the lower lock is aquired before the higher one. This eliminates the Circular wait Coffman condition because all threads have to follow the same order.

\bigskip

\textbf{Q4.2 Strategy Comparison}

\textbf{Answer:}
To start with lock ordering, it is simple and does not require retries or timeouts. It guarantess and order for the threads to reach the locks. As for timeout mechanisms, threads will retry the locks within a certain time limit. This may cause a decrease in performance because of threads constantly trying to aquire locks. Lastly, for try-lock backoff it retries aquiring the lock after waiting for a short time. This only reduces blocking a bit and increased repeated retries.

\bigskip
\textbf{Q4.3 Starvation}

\textbf{Answer:}
Lock ordering does not usually cause starvation because the threads eventually will get the needed lock. Although, if there are many threads that are wanting to aquire the lock they could be delayed if another thread aquires it first.

\bigskip
\textbf{Q4.4 Production Recommendation}

\textbf{Answer:}
For a real banking system, I would stick with lock ordering. It prevents deadlocks and is the simplest form to do so. The other strategies require retries or timeouts that could potentially cause problems. Since we know that in lock ordering have a simple pattern, it is easier for the program to be maintained.
